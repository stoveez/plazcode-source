# PlazCode 1.23 development review

Based on immutable v1.22.1 source, commit cbfe1eef5ed9f91dc6b23633d2fcba79f055ca2b. This is a development proposal, not a published release. Existing release assets and update feeds are unchanged.

Changes: guarded DOM reads and selectors in all 13 active provider adapters and two retained legacy adapters; bounded waits; guarded send acknowledgements; semantic ancestry; enforced Notion input cleanup. Saved skills include manual methods, completed-task candidates, project scopes, verified reuse, a normal AI tool for saving candidates, export, opt-in community sync and reviewed draft GitHub contributions. Skills are adapted after inspecting the current project. Opt-in shared learning refreshes approved community methods in the background at most once per hour when tasks request matching skills, avoiding a network wait on task startup. Shared lessons improve task context; no AI model weights are trained.

Explorer follows the supplied game-tree and editor layout, edits supported object properties (names, part geometry/material/color, UI layout/text/visibility) with typed validation and baseline conflict checks, defaults script auto-sync on, supports manual push and Studio comparison, and preserves local drafts across refresh. Writes require the same Studio session and source baseline, use ScriptEditorService, record Studio undo history, refuse Play mode and never automatically replay an uncertain write. ClassName and unsupported properties remain read-only; reserved/executable properties cannot be written through the object editor. The unchanged production Explorer Luau also passes transaction/rollback tests in the official Luau VM with mocked Roblox services. Filtering currently covers expanded/loaded objects. A real Studio session is still needed to verify persistent MCP execution environments, editor permission behavior and multi-place switching.

The sidebar can collapse page labels to icons with a persisted hamburger toggle. Model/UI creation recovers an unambiguous bare save response only for an active creator task, sends it through existing validation, and never implicitly inserts a model. Creator prompts now specify the tool envelope and canonical blueprint field names. Invalid or incomplete blueprints still require model correction; validation is not bypassed.

Windows app launch avoids cmd/start for executables; file/URL opening uses ShellExecuteW; command shells disable AutoRun; background launches suppress console allocation. Python Studio launcher uses the same quiet/no-AutoRun behavior. Shell behavior remains testable on Windows; the screenshot's exact refresh reproduction is not confirmed yet.

Validation before platform CI: 303 provider fault checks, 65 differential checks against v1.22.1 and 1,095 function-preservation comparisons. DOM audit covers 479 protected query/layout/attribute reads and 12 finally-protected Notion input regions. All 108 JavaScript suites pass, and the added object-property editor regression passes individually after updating the desktop fixture for the new embedded modules. Native Rust tests passed 112 checks, with two existing tests ignored; the latest full native run passes 113 tests (three library and 110 executable tests), with two existing tests ignored. A compiled Linux agent also passes real authenticated HTTP checks for skill persistence, revision conflicts, project isolation, exports, sharing defaults, task candidates and Explorer input validation. Explorer and skills UI regression suites cover persisted drafts, conflicts, explicit sharing, project adaptation and failure handling. These are fixtures, not claims of live provider, Roblox Studio or Blender compatibility.

Live-browser status: local automated Chromium/Firefox downloads previously failed with empty or corrupt files. A separate cloud Chrome can reach signed-out ChatGPT and inspect its UI, but has no patched PlazCode extension installed. Website access alone is not an end-to-end adapter test. CI runs the real browser engines against controlled provider DOM fixtures; signed-in real-provider and real-Studio/Blender checks remain release gates.

## Microsoft Defender investigation

Observed in the original release: both PlazCode.exe and the bundled Engram Windows runtime have zero-size PE certificate tables (unsigned); no UPX0/UPX1 markers; release Rust settings use size optimization, LTO and stripping. Production scripts use conservative non-mangling/non-compressing minification with AST checks. Native tools include intentional screenshot/input APIs, local command execution and child-process control. Runtime downloads, updater script execution, embedded JavaScript and low publisher/file reputation are plausible heuristic inputs, not identified causes. A GitHub provenance attestation is not an Authenticode publisher signature.

Candidate changes add real Windows VERSIONINFO metadata generated during compilation, remove shell-based app/file launch, suppress helper console windows and remove explicit PowerShell ExecutionPolicy Bypass. No antivirus exclusions, security-setting disabling, packer, byte stamping or signature spoofing are introduced. Builds must use fresh compiled executables. Enterprise execution policy now remains authoritative; deployments that require signed scripts must sign the updater with their actual certificate.

The validation workflow records Authenticode state and attempts a Defender scan of the complete freshly packaged Windows installation only if Defender is enabled on the hosted runner. Missing Defender is reported as untested, never as a clean verdict. An unsigned development build remains unsigned. The actual detection name, Defender engine/signature version, flagged file and matching SHA-256 are still needed to establish the reported false positive. The original application SHA-256 is 5b4f333791acef2b8d7ff5c4f7d7e2879189826057a94fdccd3d80b0546a3dde; the bundled Engram SHA-256 is 743037ca1415b1ab2f9f71dba9024b020020c413c2efd8c1acf1c08143772eb7. Source review cannot guarantee every detection is false or eliminate a vendor's future false positives.

Before release: build/test Windows and universal macOS, scan the exact distributable and bundled runtime files with current Defender, compare detected bytes to build provenance, submit the exact falsely detected sample to Microsoft's software-developer review, and sign with a legitimate publisher certificate if available. Do not instruct users to disable Defender. Official Microsoft references: https://www.microsoft.com/en-us/wdsi/filesubmission and https://learn.microsoft.com/en-us/windows/security/operating-system-security/virus-and-threat-protection/microsoft-defender-smartscreen/ . SmartScreen download reputation and a Defender malware detection are different outcomes.

Platform CI: the first Chromium/Firefox run passed 270 real-engine checks (135 per engine); Linux compiled and passed its validation. Windows first exposed checkout line-ending conversion in an extraction fixture; source preparation now normalizes text and Git attributes preserve LF. macOS/Windows artifacts and Defender verdict remain pending. npm audit reported zero known production tooling dependency vulnerabilities.

Release status: the user authorized publication after automated validation while accepting that live browser/Studio/Blender checks are unavailable. Platform results and actual Defender availability are recorded in release-validation-1.23.0. Earlier pending release gates above describe the development-stage investigation, not a claim that those live checks subsequently ran.
