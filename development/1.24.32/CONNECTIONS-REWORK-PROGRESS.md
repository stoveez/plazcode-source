#### Step 3 protocol sketch (a starting design, not yet built; the next chat may refine it in its own plan, but write any change down here)
- **Transport:** PlazCode spawns `blender --background --factory-startup --python <install>/blender_controller.py -- --session <id>`. One JSON object per line. Requests go to Blender's stdin, replies come from its stdout. Everything else Blender prints (banner, warnings) must not be confused with replies: the controller writes replies as lines starting with a fixed marker `PZ1 ` followed by the JSON, and the app ignores all other stdout lines (keep the last 200 of them for "Show details"). stderr is captured into the same detail log.
- **Handshake:** the controller's first reply is `PZ1 {"event":"ready","blender":"4.2.3","protocol":1,"ops":["..."],"safe":true}`. The app refuses to proceed if `protocol` is not one it knows (shows the normal "update PlazCode" message). Start-up deadline 60 s from spawn; no `ready` by then -> kill the process, report "Blender did not start" with the detail log.
- **Request:** `{"id":<int>,"type":"plazcode_op","cmd":"<op name from blender_ops.py>","args":{...}}`, plus the two legacy verbs `{"id":n,"type":"get_scene_info","params":{}}` and `{"id":n,"type":"execute_code","params":{"code":"..."}}` (the latter refused in safe mode with `{"ok":false,"error":"safe_mode","message":"Safe mode is on: free Python is blocked."}`).
- **Reply:** `PZ1 {"id":n,"ok":true,"result":{...}}` or `PZ1 {"id":n,"ok":false,"error":"<short code>","message":"<plain sentence>"}`. Unknown op -> `error:"unknown_op"`. The reply shape must be mapped by `blender_headless.rs` into exactly what `/api/blender` returns today for the socket transport, so the extension sees no difference.
- **One request at a time.** The app keeps a queue and a single in-flight request with a per-request limit (default 30 s; scene info 8 s as today; a big render or import may ask for a longer limit via an optional `"limit_s"` field, capped at 300 s). A second caller waits in the queue instead of getting the old 2 s busy error.
- **Hang and crash detection:** (a) process exit at any time -> fail the in-flight request with "Blender closed unexpectedly", keep the detail log, mark the app `needs_attention`, and restart lazily on the NEXT request (scene is lost: say so in the message); (b) per-request limit exceeded -> send a `{"type":"cancel","id":n}` line, wait 3 s, then kill and treat as (a); (c) stdout closed without exit -> treat as (a). Never auto-retry a request that may have changed the scene.
- **Shutdown:** on app exit, disconnect, mode switch or 10 minutes idle: send `{"type":"quit"}`, wait 3 s, then kill; delete the per-session temp folder. A crash of PlazCode itself must not leave Blender running: spawn it so it ends when the parent ends (Windows job object / `kill_on_drop`; on Mac/Linux set the parent-death behaviour or have the controller exit when stdin closes, which is the simplest and should be the primary mechanism).
- **Files:** per-session temp folder is the controller's working directory. Previews and screenshots are written there as PNG; the reply returns the file name only (never an absolute path chosen by the AI); the app reads it back and applies the existing size limit. "Open in Blender" saves `session.blend` via an op, then the app opens it with the normal Blender; the page never passes a path.
- **Integrity:** `blender_controller.py` and `blender_ops.py` are loaded from the install folder and listed in `integrity.rs`; a modified file must stop the headless start with the usual integrity message.
- **Test hooks:** a fake Blender (a small Python script) that speaks this protocol and can be told to: stay silent (start-up timeout), print junk before `ready`, answer slowly (request limit), exit mid-request (crash), close stdout, answer with an unknown protocol number. Every bullet above gets at least one test with it.
